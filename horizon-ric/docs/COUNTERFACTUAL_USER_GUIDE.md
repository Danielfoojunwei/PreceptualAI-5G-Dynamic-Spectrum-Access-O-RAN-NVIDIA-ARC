# Counterfactual Envelope — Operator User Guide

**Version:** 0.2.0
**Date:** 2026-05-06
**Audience:** SOC operator, network engineer, regulator running an audit
**Component:** PreceptualAI dashboard `/policies` page; `GET /api/v1/decisions/{id}`; `GET /api/v1/audit/verify`

---

## 1. What the counterfactual envelope is

For every A1 policy decision the rApp emits, the evidence chain stores not only the chosen action but also the **top-K rejected alternatives** that the planner considered. Each rejected alternative carries a structured rejection reason, a predicted outcome envelope, and a human-readable explanation. This is paradigm H1 in `PARADIGMS.md`; the schema is at `src/horizon_ric/evidence/schema.py:67-74` (`RejectedAlternative`).

The counterfactual envelope answers three questions an operator and a regulator need to be able to answer about any automated RAN decision:

1. *What did the rApp choose?* — `DecisionRecord.chosen_action`.
2. *What were the alternatives the rApp considered and rejected?* — `DecisionRecord.rejected_alternatives`.
3. *Why did each alternative lose?* — `RejectedAlternative.rejection_reason_machine` (structured) + `rejection_reason_human` (sentence).

Because the explanation is generated by deterministic templates rather than by an LLM (`src/horizon_ric/evidence/explanation.py:1-80`, see comment at line 7-8), every explanation is reproducible byte-for-byte from the structured cause and never requires its own certification.

## 2. How to view the envelope in the dashboard

1. Open the operator dashboard at `https://<rapp-host>:8083/`. The host is configured via `HORIZON_API_HOST`/`HORIZON_API_PORT` (`src/horizon_ric/rapp/lifecycle.py:227-228`).
2. Authenticate with your operator IdP. The dashboard refuses to start without `HORIZON_API_JWT_SECRET` set (`lifecycle.py:216-221`).
3. Navigate to **Policies** in the left-hand navigation. The page is `frontend/src/app/policies/page.tsx`.
4. The table lists recently emitted decisions; each row shows the decision id, timestamp, chosen action summary, and a **rejected** count column (line 141 of `page.tsx`).
5. Click any row to open the **decision drawer** on the right. The drawer renders the full `DecisionRecord` including the `rejected_alternatives[]` array (line 263-266 of `page.tsx`).

Each rejected alternative row in the drawer shows:

- the alternative's rank (1 = closest runner-up),
- a JSON view of the rejected action,
- the predicted outcome envelope it would have produced (SLA risk at 30s/1min/5min, gateway loads, NTN capacity used, energy kWh),
- the structured rejection reason (`primary_cause`, `primary_metric`, `predicted_value`, `threshold`, `horizon`),
- the human-readable rejection sentence.

## 3. How to interpret each rejection reason

The rejection reason is a `RejectionReasonMachine` (`evidence/schema.py:47-65`). Each instance has:

| Field | Meaning |
|---|---|
| `primary_cause` | One of the nine canonical causes (see §4) |
| `primary_metric` | The specific KPI or counter that triggered (e.g. `gateway_load_G3`, `compute_cpu_edge_5`) |
| `predicted_value` | The forward-simulated value the planner predicted for this alternative |
| `threshold` | The threshold the value would have crossed |
| `horizon` | One of `30s`, `60s`, `300s` — the prediction horizon |

To interpret: the alternative was rejected because, at horizon `H`, the planner predicted that `primary_metric` would reach `predicted_value`, which crosses the operator-configured `threshold` for that `primary_cause`.

## 4. The nine canonical rejection causes

Defined in the `Literal` at `src/horizon_ric/evidence/schema.py:50-60` and templated at `src/horizon_ric/evidence/explanation.py:16-56`. These are exhaustive — no other `primary_cause` value can be persisted, because the schema rejects unknown literals at validation.

| # | `primary_cause` | When it fires | Template line in `explanation.py` |
|---|---|---|---|
| 1 | `gateway_overload` | The alternative would push a gateway's load past its safety threshold at the named horizon | line 17-21 |
| 2 | `sla_breach_predicted` | The alternative would push the SLA breach probability for some bearer past the configured threshold | line 22-25 |
| 3 | `compute_overload` | The alternative would push edge-compute utilisation past the ceiling, risking AI-workload queueing delays | line 26-30 |
| 4 | `energy_cost` | The alternative's energy cost exceeds the budget without compensating SLA gain | line 31-35 |
| 5 | `ntn_capacity_exhausted` | The alternative would push NTN (non-terrestrial) capacity past its reserve target | line 36-39 |
| 6 | `spectrum_unavailable` | Spectrum allocation conflict — predicted utilisation exceeds allowed | line 40-43 |
| 7 | `constraint_violation_hard` | The alternative would breach a hard regulatory constraint (LI, EPFD, ITU-R mask). **This is unconditional** — see `src/horizon_ric/policy/li_constraint.py:30-34` | line 44-47 |
| 8 | `constraint_violation_soft` | The alternative would breach a soft operator-policy constraint (preference, not regulation) | line 48-51 |
| 9 | `policy_oscillation` | The alternative would induce a policy change-rate above the anti-oscillation threshold | line 52-55 |

A `primary_cause` of `constraint_violation_hard` is a **hard rejection** — the alternative is regulatorily impossible, not merely undesirable. The rApp will never choose an alternative with a hard violation; it appears in the rejected envelope only to show that the alternative was considered and excluded.

How to read this:

- The chosen action moved the slice to gateway G2 in DE, predicting a 7-11% SLA breach risk envelope.
- Rank-1 rejected: G3 would have produced a slightly **lower** SLA risk envelope (5-8%), but its predicted load (94%) crosses the 90% gateway-overload threshold at 60 s. The rApp chose the slightly-higher SLA risk of G2 to keep G3 within safety bounds. This is the kind of trade-off an operator wants visible in the audit trail.
- Rank-2 rejected: would have anchored the (LI-protected) slice in FR, which is not on the warrant's allowed jurisdiction list; the LI constraint hard-refused. See `src/horizon_ric/policy/li_constraint.py:129-146`.

## 7. How a regulator reproduces a decision

A regulator with a tenant-scoped JWT (issued by the operator's IdP for the duration of the audit) reproduces a historical decision as follows.

### 7.1 Verify the audit chain is intact

```http
GET /api/v1/audit/verify
Authorization: Bearer <auditor-jwt>
X-Tenant: <operator's tenant id>
```

Handler at `src/horizon_ric/rapp/api_v1.py:392-404`. The response carries `ok` (bool), `records_checked` (count), `first_bad_index` (index of the first broken record, or `-1` if the chain is intact). The chain walk uses the formula at `src/horizon_ric/evidence/store.py:75-79` (`sha256(prev_hash || canonical_json(record))`), starting from the all-zero hash (line 48).

If `ok == false`, the auditor must NOT trust any record at or after `first_bad_index`. This is the integrity test that NIST CSF DE.AE-02 calls for and that the GDPR DPIA (`docs/compliance/gdpr_dpia.md` §4.2) names as the deletion-detection control.

### 7.2 Fetch the specific decision

```http
GET /api/v1/decisions/{decision_id}
Authorization: Bearer <auditor-jwt>
X-Tenant: <operator's tenant id>
```

Handler at `src/horizon_ric/rapp/api_v1.py:340-347`. Returns the full DecisionRecord including `rejected_alternatives`, `model_versions`, predicted vs `actual_outcome_30s/1min/5min`, and any `operator_override` flag.

### 7.3 Reproduce the predicted outcomes

Using `model_versions.encoder`, `model_versions.risk_heads`, etc., the auditor can match the corresponding `checkpoints/<model>_v<version>.pt` artefact (with sha256 verified against the `checkpoints/<model>_v<version>.md` model card per `tests/test_ts28105_model_card_emit.py`). Replaying the encoder + risk heads on the input state reproduces the predicted outcome envelope.

The input state is referenced by `state_hash` (`evidence/schema.py:107`) and optionally by `state_blob_uri` (line 108) — the operator's object-store URI of the full `z_resource` snapshot.

### 7.4 Reproduce the rejection

For any rejected alternative, the auditor:

1. Reads `rejection_reason_machine` from the record.
2. Confirms `predicted_value` against the threshold table the operator has configured (held in the operator's policy config — typically alongside `deploy/prometheus/sla_rules.yml`).
3. If `primary_cause == constraint_violation_hard`, the auditor confirms the constraint catalogue (`LIJurisdictionRule` set, EPFD masks, ITU-R masks) was the one in force at `timestamp`. This requires the operator to retain the constraint-catalogue snapshot at every rApp boot — currently captured by the model-version tag `constraint_layer` in `ModelVersions` (`evidence/schema.py:28`).

If any step diverges, the auditor has independent evidence that the rApp's record does not match its actual decision logic — i.e. evidence of misconfiguration or tamper.
